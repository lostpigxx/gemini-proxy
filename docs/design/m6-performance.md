# 设计：M6 性能打磨的测量口径与优化排序

> 日期：2026-09-21（2026-09-22 修订：§1.6、§1.7 两个新陷阱，以及被它们污染的
> §2、§3.1、§3.3、§4 的重测数据）
> 状态：进行中
> 范围：基准环境（`scripts/bench.sh`、`scripts/bench-env.sh`）、M6 验收口径的修正、
> profile 结论与候选优化的重新排序。

这一页记录的是**分叉**，不是流水账：开发计划里 M6 的验收标准和候选优化清单，在真正把仪器
搭起来之后有一半站不住了。下面逐条说明改成了什么、为什么。

## 1. 先修仪器：七个已经产出过错误数字的陷阱

M6 的第一项任务是"基准环境固化"。固化之前先做的事是**证伪已有的基线**——M3/M4/M5 的表格里
有一部分数字测的不是代码。§1.6 和 §1.7 更狠一点：它们证伪的是本文档自己第一版里的数字。

### 1.1 GET 命中率（"双峰吞吐"的真正根因）

记忆和开发计划里都把直连 `-P 16` 在 2.0M 与 3.3M 之间的跳变归因于"单线程 redis-server 的
核放置随机"。这是错的。真正的原因是 **GET 打没打中**：`redis-benchmark -t get -r 1000000`
打一个没填过的库，全部是 miss，而 `$-1` 的回复字节数只有 `-d 32` 命中回复的四分之一。
同一台机器同一秒内测：

| keyspace | GET rps（直连，`-c 50 -P 16 -d 32`） |
|---|---|
| 空 | 3,996,802 |
| 填满 | 1,537,042 |

**2.6 倍**。前几个里程碑里凡是没说清楚库填没填的 GET 数字，都不能跨轮比较。

处置：`bench.sh` 每轮开跑前用 `KEYSPACE * 4` 次随机 SET 填库（coupon collector，覆盖率
≈98%），跑完 `DBSIZE` 并把结果打进报告；低于 95% 直接告警。命中率从"默认假设"变成"在案记录"。

**且要对每个不同的 endpoint 各填一次。** arm 之间通常共用后端，重复填只是冗余；但
standalone-vs-cluster 的两个 arm 各有各的存储，只填 arm 0 会让另一个每次 GET 都 miss——同
一个陷阱，方向反过来，会读成"集群路径快 2.6 倍"。

### 1.2 rps 被计时精度量化

redis-benchmark 报告的 rps 来自它自己 250 ms 的进度 tick，所以一次 3 秒的跑动只能落在
约 8% 的台阶上（实测所有值都落在 1.751 / 2.752 / 3.002 / 3.253 / 3.503 秒这张 0.25 秒的
网格上）——比 M6 想测的任何东西都粗。

处置：`bench.sh` 自己掐表算 wall-clock rps，工具自报的值留在 `results.tsv` 的
`rps_reported` 列里备查。在网格点上两者相差 0.06% 以内，离开网格点时只有 wall-clock 是对的。

### 1.3 压测端才是瓶颈

给 redis-benchmark 四个核时，**每个 arm 都读回同一个 363,504 rps**，直连 `-P 16` 从 2.86M
塌到 1.43M。测的是客户端，不是服务端。给到八个核（4 线程）后 `-P 16` 才能逐轮复现。

### 1.4 没固核 + `--cpu-affinity` 静默失效

`--cpu-affinity` 从 0 开始编号 CPU，于是 `taskset -c 5-8 proxyd --cpu-affinity -w 4` 实际请求
的是 CPU 0..3，每次 `pthread_setaffinity_np` 都返回 EINVAL，返回值又被丢掉——worker 全程在飘，
某些轮次两个 worker 挤一个核，表现为轮次间 8% 的吞吐摆动。已修（`worker_pool.cpp` 现在读
`sched_getaffinity` 拿到的实际掩码，按序取第 i 个可用核）。

同理，**集群 master 不能和单机后端共核**：原来两者都落在 cpu 2，standalone-vs-cluster
一轮里空闲那侧的 cluster cron 正好压在忙碌那侧的 server 上，轮次离散度到过 137%。现在
`VKP_CPUS_BACKEND=1,2,3,4`，单机后端占 index 0，三个 master 占 1..3。

固核之后（后端独占一核、worker 一核一个、压测端独占 8 核），高负载下的**轮次间 rps 离散度从
7~9% 降到 0.0~0.5%**。固核在这里不是调优手段，它是仪器本身。

### 1.5 跨轮比较

沿用 M5 的结论并写进了 `bench.sh` 的结构：脚本**不拥有任何进程**，只接受重复的
`--arm label=host:port[@pid]`，并在**每个场景内部**交替跑各个 arm，使两个被比较的数字相隔几秒
而不是几分钟。`--baseline` 给出的跨轮 diff 明确标注为 advisory。

### 1.6 残留进程 + SO_REUSEPORT：测的是几个二进制的混合

**本文档第一版的 §2 基线表、§3.3 热点表和 §4 的 A/B 结论都是这个 bug 的产物。**

`bench-env.sh down` 用的是 `pkill -x proxyd`，而 A/B 要比较的二进制是复制成不同文件名的
（`m6-B-before.proxyd`、`m6-A-clockfix-before.proxyd`）。`ps`/`pkill` 匹配的是 `comm`——
**可执行文件名截断到 15 个字符**——`m6-B-before.proxyd` 的 comm 是 `m6-B-before.pro`，于是
`pkill -x proxyd` 一个都没匹配上，每次 A/B 都留下一批活的旧进程。

扫 `/proc/net/tcp` 加 `/proc/*/fd` 的 inode 映射，发现**同时有四个 proxyd 绑在 6380 上**，
6381 上四个，6382 上三个，其中还有更早那轮 clock A/B 留下的 pid 23281。SO_REUSEPORT 不会
拒绝这种 bind，它**静默地把新连接摊给所有监听者**；而 `bench.sh` 只按 `@pid` 统计其中一个
进程的 CPU。结果就是一个 arm 读起来比它自己的孪生兄弟便宜 40%。

发现过程值得记一笔：slot 缓冲复用的第一次 A/B 读出 1.5~1.9 倍的**劣化**，数字还只落在两个
固定值上。把同一个 `before` 二进制同时放进 slot 1 和 slot 3 跑（位置对照），两个理应相同的
arm 差了 40%——于是问题从"改动有没有效"变成"仪器在测什么"。

处置：`live_proxies()` 按 `argv[0]`（我们自己传的完整路径）扫 `/proc` 列出真实 pid，按 pid
发信号；`wait_gone()` 等真正退出、10 秒后升级 SIGKILL；`cmd_proxy` 里再加一道端口占用检查兜底。
另外要跳过僵尸：容器 PID 1 是 `sleep infinity`，从不 reap，死掉的 proxyd 会永远留在 /proc 里
（现在机器上躺着 17 个），按存在性等待会永远等不完；僵尸不持有 socket，无害。

修完之后位置对照：两个相同二进制在不同 slot 上的 CPU/请求相差 **0.6~0.8%**。

### 1.7 CPU 计量本身的分辨率：tick 采样的 ±5%

修完 §1.6 之后仍有一件事不对：rps 的轮间离散度是 **0.0%**，而同一批跑动的 CPU/请求离散度是
**5~9%**。同一个仪器不可能对同一件事既精确到 0.0% 又抖动 9%——抖的不是机器，是计量方式。

`/proc/pid/stat` 的 utime+stime 是 **100 Hz tick 采样**的：`-P 16` 一轮 3 秒，四个 worker 各
只有约 22% 占空比，整个测量建立在约 265 个 tick 上，二项采样误差
`sqrt(300*0.22*0.78)*4/265 ≈ 5%`。这比 M6 清单上任何一项优化都大。

处置：改读 `/proc/pid/task/*/schedstat` 的第一个字段——调度器累计运行时间，**纳秒，实测值不是
采样值**。同一二进制两次跑动的偏差从 5~9% 降到 0.2~1.4%。

即便如此，`-P 16` 下 7 轮取中位数的可分辨下限仍约 **±1~2%**（用两个相同二进制的对照 arm 实测
得到，见 §6、§7）。**低于这个幅度的改动，单看一次的幅度判不了**——只能靠对照 arm 加多次
独立复现，见 §7 的做法。

## 2. 验收口径：吞吐比不是良定义的，改用 CPU µs/请求

开发计划给 M6 定的目标是"吞吐 ≥ 直连的 92%"。在这套仪器下这个指标测不出它想测的东西：

- `-c 50 -P 1`：redis-benchmark 是闭环压测，吞吐 = 并发数 / 延迟，50 连接时客户端先饱和，
  **所有 arm 都读回 ~363k**，与 proxy 无关。
- `-c 200 -P 1`：proxy 比直连**快 41%**（545k vs 386k），因为它把 200 个客户端 socket 汇聚
  到一条做了写合并的后端连接上。这时候"相对直连的比值"衡量的是**后端单线程 socket 处理能力**，
  不是 proxy 的开销。

也就是说这个比值既可能因为客户端饱和而恒为 1，也可能因为 proxy 帮后端省了活而大于 1。
两种情况下它都不随 proxy 的代码质量单调变化。

**替代指标：proxy 每请求消耗的 CPU 微秒**（`label=host:port@pid`，取 schedstat 纳秒差）。
它只计 proxy 自己的开销，不受后端和压测端的饱和行为影响，且对优化单调响应。吞吐与 p99 仍然
照测照报，但**判定优化是否生效以 CPU/请求为准**。

### M6 起始基线

固核、逐 endpoint 填库、wall-clock rps、schedstat 计 CPU。rps/p99 为 3 轮中位数，
CPU/请求为 7 轮中位数。集群为 3 主 0 从，各占一核。

| 场景 | 直连 rps | 单机 rps | 集群 rps | 直连 p99 | 单机 p99 | 集群 p99 | 单机 CPU µs/req | 集群 CPU µs/req |
|---|---|---|---|---|---|---|---|---|
| SET P=1 d=32 c=200 | 386,652 | 544,725 | 510,240 | 0.767 | 0.471 | 0.463 | 6.263 | 7.296 |
| GET P=1 d=32 c=200 | 386,221 | 544,860 | 507,781 | 0.759 | 0.463 | 0.455 | 6.136 | 7.344 |
| SET P=16 d=32 c=50 | 1,331,095 | 1,535,833 | 2,218,113 | 0.639 | 0.559 | 0.471 | 0.520 | 1.164 |
| GET P=16 d=32 c=50 | 1,426,051 | 1,663,743 | 2,218,029 | 0.615 | 0.543 | 0.463 | 0.506 | 1.149 |

（直连 SET `-P 16` 一行的轮间离散度有 7.2%，其余各行 ≤0.5%；这一格当区间读。）

三点要说清楚：

- **p99 每一行都低于直连**，不是"不超过直连 +15%"。原因同上——汇聚 + 写合并对后端是净减负。
- **集群吞吐高于单机**（`-P 16` 下 133%）不是 proxy 的功劳，是集群那侧有三个后端各占一核而
  单机只有一个。拿来对"集群 ≥ 单机 80%"这条验收标准交差是自欺欺人，真正的口径是下面一行。
- **集群的 CPU/请求是单机的 2.14~2.27 倍**（`-P 1` 下 1.20 倍）。这才是集群路径的真实代价。

## 3. profile：钱花在哪里

### 3.1 用户态 / 内核态划分

容器里的 perf 只能做用户态采样（`task-clock:upppH`），所以先量总的用户/内核劈分：

| 场景 | | 用户态 | 内核态 | 用户态占比 | 合计 µs/req |
|---|---|---|---|---|---|
| P=16 c=50 | 单机 | 1420 ms | 2830 ms | **33%** | 0.531 |
| P=16 c=50 | 集群 | 2620 ms | 6490 ms | **29%** | 1.139 |
| P=1 c=200 | 单机 | 880 ms | 17300 ms | **5%** | 6.060 |
| P=1 c=200 | 集群 | 760 ms | 21400 ms | **3%** | 7.387 |

**`-P 1` 下 proxy 有 95~97% 的 CPU 在内核里。** 这个工况下所有用户态微优化加起来的天花板是 5%。

集群相对单机每请求多花的 0.61 µs 里，用户态只占 0.15 µs，**内核态占 0.46 µs（75%）**；
`-P 1` 下用户态甚至是负的（760 vs 880 ms），增量 100% 在内核。集群的代价主要不是路由计算。

### 3.2 syscall/请求：已经不是问题

开发计划把"syscall 次数/请求"列为重点检查项，并据此把 provided buffer ring + multishot recv
排在候选优化的第二位。实测（strace 计数 + 同窗口内后端 `total_commands_processed` 增量；
清理环境后重测，与第一次的 27 / 51 一致）：

| 场景 | 窗口内请求数 | `io_uring_enter` | **请求/syscall** |
|---|---|---|---|
| 单机 P=16 c=50 | 8,406,193 | 309,588 | **27.2** |
| 集群 P=16 c=50 | 6,951,804 | 130,940 | **53.1** |

批量提交（`poll()` 里的 `io_uring_submit_and_wait_timeout`，`submit()` 不单独进内核）已经把
27~53 个请求摊到一次系统调用上。**内核时间不是系统调用入口开销，是 loopback TCP 栈真正在搬
每请求 4 次 socket 操作**（client→proxy、proxy→backend、backend→proxy、proxy→client）。

两个推论：

- provided buffer ring / multishot recv 攻击的是 SQE 条数和入口次数，这两项都已经摊薄了一个
  数量级，**从候选清单的第二位降到末位**。
- 开发计划里"集群模式丢失了写合并"这个前提**不成立**：集群的请求/syscall 反而是单机的
  1.95 倍。集群贵在把一条后端连接拆成三条，每条搬的字节更少、包更碎，而不是贵在没合并。

## 4. 已实施：每请求的时钟读取改用 loop 缓存值

`backend_conn::push()` / `deliver_head()` / `fail_all()` 里的
`std::chrono::steady_clock::now()` 换成 M5 引入的 `loop_.now()`（每次 loop 迭代缓存一次的
`steady_clock` 时间戳）。

**正确性论证**：这三处的时间戳只有两个用途——请求超时判定，和 `backend_duration` 直方图。
陈旧度上界是一次 loop 迭代，量级是微秒；超时以秒计，直方图的分辨率也远粗于此。并且一个请求
的两个时间戳（`push` 打的 deadline 与 `deliver_head` 读的 now）之间必然隔着至少一次 poll，
所以采样区间不会塌成 0。

**A/B 结果**（清理环境 + schedstat 计量，同轮交替，7 轮取中位数）：

| 场景 | 改前 CPU µs/req | 改后 | |
|---|---|---|---|
| GET P=16 c=50 | 0.5347 | 0.5058 | **94.6%** |
| SET P=16 c=50 | 0.5422 | 0.5199 | **95.9%** |
| GET P=1 c=200 | 6.1948 | 6.1356 | **99.0%** |

吞吐不变（后端受限）。`-P 16` 省 4~5%，`-P 1` 省 1%——与 §3.1 的用户态占比一致。

提交 b903b6c 当时报的是"`-P 16` 93.1%"，那是污染环境下的数字；清理重测后结论方向一致、
幅度接近（94.6%），**这一项的结论成立**。这也是被 §1.6 污染的结论里唯一站住的一个。

## 5. 候选优化的重新排序

按 §3.3 实测"能动的总 CPU"排：

1. ~~**RESP 解析器热路径**（用户态约 25%，`-P 16` 下折合总量约 8%）。`dispatch_header` 与
   `parse` 两个函数就占了用户态的 21%。方向：CRLF 搜索向量化、把逐字节的类型分派换成
   查表、减少 `parse`/`finish` 之间重复走的 span。触碰解析器必须过 fuzz 短跑。~~
   **已做，见 §7**——但列的三个方向一个都没用上：CRLF 搜索本来就是
   `string_view::find('\n')`，落到 libc `memchr`，早就是向量化的；类型分派是个 `char` 上的
   `switch`，编译器已经出跳转表。真正剩下的是整数行解析。
2. ~~**`find_command` 热路径**（用户态约 10.7%，折合总量约 3.5%）。`std::toupper` 是
   locale-aware 的 libc 调用、不内联；`std::lower_bound` + `memcmp` 的比较链可以换成
   constexpr 完美哈希。便宜且确定。~~ **已做，见 §7**（用首字母区间 + 长度过滤，不是完美哈希）。
3. **`frame_pool` 的分配/释放**（用户态 5.3%/5.8%）——协程帧内存池调参。
4. **集群路径**：2.14 倍的代价里 75% 在内核（§3.1），所以用户态那点路由计算（`route_slot`
   2.38%）不是重点。能动内核时间的只有"减少后端方向的 socket 操作次数或包数"。这是 M6 里
   最有价值也最难的一项，需要单独一页设计。
5. **provided buffer ring + multishot recv/accept、recv bundle**——降级至此，理由见 §3.2。
   若要做，仍须 ring 与 multishot 成对做（M2 交接结论）。

`-P 1` 工况（用户态 3~5%）对 1、2、3 基本免疫，这几项的收益只体现在高 pipeline 深度下。

## 6. 已否决：client_conn 的 slot 缓冲复用

集群模式下每请求要 `slots_.back().request.assign(msg.raw)`（MOVED/ASK 可能要重放），
乱序回复还要 `reply.assign(frame)`——§3.3 里集群侧的 `operator new[] + delete[] + _M_mutate`
合计 5.7% 用户态，正是这两处。做了一版 32 槽的 `std::vector<std::string> spare_` 复用池
（`adopt`/`recycle`，标准库分配器恒等传播所以 move 是 noexcept；单机模式不 reserve，容量 0
时两个函数都立即返回）。

**A/B 判定为无效，已回滚。** 集群模式 7 轮，带一个**同二进制对照 arm**：

| 场景 | 无池 | 有池 | 无池（对照） | 有池/无池 | 对照/无池 |
|---|---|---|---|---|---|
| GET P=16 c=50 | 1.1533 | 1.1336 | 1.1439 | 98.3% | 99.2% |
| SET P=16 c=50 | 1.1690 | 1.1597 | 1.1594 | 99.2% | 99.2% |
| GET P=1 c=200 | 7.3228 | 7.3089 | 7.3642 | 99.8% | 100.6% |

两个**完全相同**的二进制之间就差 0.6~0.8%，而改动带来的差异最多只在三个场景里的一个上
比对照多出 0.9%。这在 §1.7 给出的 ±1~2% 分辨率之内，**测不出来就是没有**。30 行缓冲复用
代码换不到可证明的收益，不留。

顺带校准了两件事：一是仪器的可分辨下限（对照 arm 是量它的正确办法，以后每次 A/B 都带一个）；
二是 §3.3 说的集群侧 5.7% 用户态分配开销，折合总量只有 1.7%——即使完全消除也不值得为它增加
复杂度，这条路整个封掉。

## 7. 已实施：RESP 整数行与命令查表的热路径

§5 的第 1、2 项，**合并成一次改动一起测**。理由是 §1.7：仪器的可分辨下限是 ±1~2%，而这两项
各自折合总量只有 1~3%，分开测就是两次都落在噪声里。

### 改动

**`resp::parse_i64` 加纯数字快路径**（`src/resp/parser.cpp`）。每转发一条命令它至少走三次
（`*N`、命令名的 `$len`、每个参数的 `$len`），而这些行实际上永远是一到三位数字。18 位以内的
十进制数不可能溢出 int64，所以累加不需要逐位溢出检查——那正是 `from_chars` 在做的主要工作。
带符号、19 位以上、含非数字的输入一律落回 `from_chars`，边界情况仍然只有一个归属者。

**`find_command` 换成首字母跳转 + 长度过滤**（`src/proxy/command_table.cpp`）。原来是
`std::lower_bound` 在 200 多行上做约 8 次 `string_view` 比较，每次都是一个不内联的 libc
`memcmp`；大小写折叠还调了 locale-aware 的 `std::toupper`。改后是两张 consteval 侧表：
`kFirstRange[26]` 把首字母映到一段连续区间（表按名字排序，连续性由构造保证），`kNameLen[]`
让扫描以单字节拒绝候选，而不必把整个 `command_info` 拖进 cache。只有长度命中才走 `memcmp`，
实测一到两次而不是八次。

大小写折叠写成 `c - (unsigned(c - 'a') < 26 ? 0x20 : 0)`，而不是诱人的单指令 `c & ~0x20`：
后者会把 0x7b..0x7f 一起映到 `[ \ ] ^ _`，于是 `EVAL\x7fRO` 能匹配上 `EVAL_RO`。测试里钉死了
这一条。

三条 `static_assert` 兜住漂移：表长 < 256（侧表索引是 `uint8_t`）、所有名字以 A-Z 开头、以及
**穷举**验证每条命令都能经由索引查到它自己那一行。最后一条放在编译期是有意的——运行时测试
只能抽样，编译期能在新增的一行放错位置的当下就报错。

### A/B 结果

`-P 16`，同轮交替，带**同二进制对照 arm**（§6 的教训）。`-P 1` 不在表内：§3.1 说那里用户态
只占 3~5%，这两项按构造就动不了它；7 轮实测也确实落在对照的摆动里。

| 场景 | 改前 | 改后 | 对照（改前的二进制） | 改后/改前 | 对照/改前 |
|---|---|---|---|---|---|
| 单机 SET P=16（7 轮） | 0.5247 | 0.5090 | 0.5260 | **97.0%** | 100.2% |
| 单机 GET P=16（7 轮） | 0.5103 | 0.5057 | 0.5105 | **99.1%** | 100.0% |
| 单机 SET P=16（15 轮） | 0.5234 | 0.5100 | 0.5298 | **97.4%** | 101.2% |
| 单机 GET P=16（15 轮） | 0.5102 | 0.5056 | 0.5095 | **99.1%** | 99.9% |
| 集群 SET P=16（15 轮） | 1.1587 | 1.1484 | 1.1628 | **99.1%** | 100.4% |
| 集群 GET P=16（15 轮） | 1.1554 | 1.1344 | 1.1469 | **98.2%** | 99.3% |

**判据是符号，不是幅度。** 单看幅度，1~3% 压在 §1.7 给出的分辨率上沿，任何单次测量都不足为凭。
但这六个 `-P 16` 单元里，"改后"arm 每一次都是三条里最低的——零假设下概率 (1/3)⁶ ≈ 0.14%。
而 `-P 1` 的两个单元里它不是最低的，这正是 §3.1 预测的（那里用户态只有 5%，这两项无从下手）。
信号出现在它该出现的地方，噪声出现在它该出现的地方。单机的两次独立测量（轮数不同、各自重新
fill）比值一致到 0.4 个百分点，这比任何一次的幅度都更能说明问题。

幅度也对得上账：`-P 16` 单机用户态占 33%，`find_command + memcmp + toupper` 占用户态 10.7%
（§3.3），折合总量 3.5%，这次并没有把它清零；加上 `parse_i64` 在 `dispatch_header` 里的那
一份，2~3% 是该有的量级。SET 比 GET 省得多也有机制上的解释：SET 比 GET 多一个参数，就多一行
`$len`，也就多一次 `parse_i64`——省下的量随参数个数走。集群侧只有约 1%，同样符合预期：那里
`find_command` 只占用户态 2.46%，用户态又只占 29%。

fuzz 短跑（CLAUDE.md 要求）：`resp_parser` 501 万次、`admin_http` 8231 万次，无 crash；
顺手把语料 `-merge=1` 精简（813→466、28→23，覆盖不变）。
