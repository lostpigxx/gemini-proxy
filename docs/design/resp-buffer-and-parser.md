# 设计：连接读缓冲与 RESP 解析器（M1）

> 日期：2026-08-24
> 状态：定稿
> 范围：`read_buffer`（连接读缓冲）、RESP2/3 增量浅解析器、深解析器、序列化器的所有权模型与 API 形态。

## 1. 核心矛盾

零拷贝要求解析结果以视图（`std::string_view`）指回读缓冲；但缓冲会因 recv 追加而扩容/搬移，
指针随时可能失效。增量解析要求「恢复解析不重扫已扫过的字节」，即解析状态必须跨多次 recv 存活。
这两点共同决定了下面的所有权模型。

## 2. 所有权与稳定性模型

**唯一所有者**：`read_buffer` 是缓冲内存的唯一所有者，每连接一个，生命周期与连接绑定。
解析器不拥有任何内存，只产出视图与偏移。

**关键不变量（整个设计的基石）**：

1. **窗口起点 = 当前消息起点**。调用方只在完整消息边界处 `consume()`，因此每次传给解析器的
   可读窗口（`readable()`）总是从「正在解析的这条消息的第 0 字节」开始。
2. **解析器内部只存相对偏移**（相对窗口起点），不存指针。缓冲扩容或压缩搬移只改变窗口的
   内存地址，不改变窗口内容与各字节的相对位置，因此解析中间状态天然免疫搬移。
3. **窗口在同一条消息的解析过程中只增不减**：两次 `parse()` 调用之间，新窗口必须是旧窗口的
   前缀扩展（追加了新收到的字节）。这由「只在消息边界 consume」保证。

**视图生命周期**：`parse()` 返回 `complete` 时产出的 `message_view`（整条消息的 raw 视图 +
命令参数视图数组）指向缓冲内部，仅在下一次对 `read_buffer` 的写操作（`prepare`/`commit`/
`consume`）之前有效。proxy 的用法是：解析完成 → 立即把 raw 字节转发（或拷贝命令名等少量
需要留存的数据）→ `consume()` → 继续。视图从不跨越 IO 边界存活。

## 3. read_buffer API 与扩容策略

```
class read_buffer {
  std::span<char> prepare(std::size_t min_free);  // 保证尾部至少 min_free 可写，返回可写区
  void commit(std::size_t n);                     // recv 写入 n 字节后调用
  std::string_view readable() const;              // 当前可读窗口
  void consume(std::size_t n);                    // 只允许在消息边界调用
};
```

- 底层是单块连续内存（`head_`/`tail_` 两个游标），初始 8 KiB。
- `prepare` 空间不足时：先尝试**压缩**（把 `[head_, tail_)` memmove 到开头——head_ > 0 才有
  意义），仍不足则按 2 倍扩容到能容纳「未消费数据 + min_free」的最小二次幂。
- `consume` 恰好清空缓冲时把游标归零（免费的压缩）。
- 不做自动收缩：一条连接曾经收过大消息就保留大缓冲，属于可接受的内存换性能；收缩策略留 M6
  用数据决定。

## 4. 浅解析与深解析分离

proxy 数据面 99% 的工作是**透传**：只需要消息边界（决定转发多少字节、FIFO 配对响应）、
命令名（查命令表）、参数位置（M4 提 key 算 slot）。为此：

- **浅解析器 `resp::parser`（数据面热路径）**：增量状态机，扫描出一条完整 RESP 值的边界，
  不物化任何树。当顶层是「bulk 数组」（即标准命令形态）时，顺手记录每个顶层 bulk 的
  payload 偏移，完成时以 `args[]` 视图数组暴露（`args[0]` 即命令名）。非命令形态
  （嵌套、顶层非数组等）只给边界，`is_command = false`。
- **深解析器 `resp::parse_tree`（控制面冷路径）**：输入一条**已确认完整**的消息（浅解析器
  先定边界），递归下降物化成 `resp::value` 树。用于 proxy 自身要理解的响应
  （M4 的 `CLUSTER SHARDS` 等）。不做增量——控制面消息先攒完整再解析，简单压倒一切。

两者共享同一套 `resp::limits` 防御限制。

## 5. 浅解析器状态机

状态只有两个：`header`（在读一行 `<type byte>...\r\n`）与 `bulk_body`（在等 bulk payload +
CRLF）。聚合类型（array/map/set/push/attribute）不引入状态，用一个显式栈
`{剩余子元素数, 是否 attribute}` 表达嵌套；bulk 的 payload 不逐字节扫描（长度已知，只做
边界与 CRLF 校验），头部行用 `memchr('\n')` 找行尾。

**不重扫保证**：`pos_` 记录已检查到的位置；`need_more` 时 `pos_` 停在窗口末尾，下次从新数据
处继续找 `\n`。恶意方逐字节喂一条超长行也只有 O(n) 总代价。

**attribute（`|N`）的特殊性**：RESP3 中 attribute 是「附着在下一个值上的元数据」，不是独立
的一条回复。若把它当独立消息，FIFO 响应配对就会错位。处理：`|N` 入栈 2N 个子元素，弹栈时
**不向父级传播「值完成」**——所在槽位仍然欠一个真正的值。消息边界因此把
「attribute + 被注解的值」算作一条。

**RESP2 null 兼容**：`$-1`（null bulk）与 `*-1`（null array）都是合法的完整值。

**不支持项（显式报协议错误，不是静默吞掉）**：

- RESP3 streamed/chunked 类型（`$?` + `;` 分块、聚合的 `?` 长度）：valkey 实际不发，收到即
  `streamed_not_supported`。若未来需要再立项。
- inline command（无类型字节的裸文本行）：按计划留 TODO，报 `unknown_type_byte`。

## 6. 防御限制（resp::limits，全部可配）

| 限制 | 默认值 | 防什么 |
|---|---|---|
| `max_message_bytes` | 512 MiB | 单条消息把缓冲撑爆（含「聚合头声称天文数字元素数」的变体：不预付内存，等数据到达时按已扫描字节数触发） |
| `max_bulk_bytes` | 512 MiB | 单个 bulk 超长（在读头部时即可拒绝，不等 payload） |
| `max_line_bytes` | 64 KiB | 无 CRLF 的超长行（simple string / 数字行） |
| `max_nesting_depth` | 32 | 深嵌套打爆解析栈/深解析递归 |
| `max_command_args` | 1 Mi | 顶层参数偏移数组无界增长。超限不报错、只放弃参数记录（`is_command=false`），因为后端响应也可能是巨型顶层数组，报错会误伤透传 |

解析器自身零分配（除聚合栈与参数偏移数组，均为复用的 vector，摊还后稳态零分配）。

## 7. 校验的严格度

原则：**proxy 会解读的字段严格校验，只透传的字段宽松校验**。

- 严格：所有长度头与 `:` 整数（完整 int64 语法，`std::from_chars` 全量消费）；`#` 只接受
  `t`/`f`；`_` 后必须空行；行必须以 `\r\n` 结束（裸 `\n` 报错）。
- 宽松：`,`（double）与 `(`（big number）只要求行非空，不验证数字语法——proxy 不解读它们，
  过度严格只会在 valkey 换格式时误杀透传。深解析器解读 double 时才严格。

## 8. 序列化器

只服务 proxy 自身的少量回复（错误、`+OK`、管理命令响应），追加式写入 `std::string`：
`append_simple_string / append_error / append_integer / append_bulk / append_array_header /
append_null(ver)`。热路径转发不经过序列化器（原样透传字节）。

## 9. 被否决的替代方案

- **解析结果拷贝出缓冲（无视图）**：每请求两次拷贝（进+出），直接违背性能目标。
- **环形缓冲**：消息可能跨环边界，视图无法连续，需要「读时拼接」或限制消息不跨界（等价于
  压缩搬移），复杂度不换收益。
- **解析器持缓冲（parser owns buffer）**：IO 层 recv 需要向缓冲写，所有权在解析器会让 IO
  与解析互相持有对方，M2 的 proactor 接口（提交 buffer + 完成通知）要求缓冲归连接所有。
- **浅解析也物化消息树**：树节点分配 + 指针追逐正是 twemproxy 等老代理的热点，本设计的
  出发点就是消灭它。
